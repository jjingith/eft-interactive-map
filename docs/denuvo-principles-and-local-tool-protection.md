## 0. 先给结论

1. **Denuvo Anti-Tamper 和 Denuvo Anti-Cheat 是两个产品**：前者是用户态的反篡改/反逆向层，保护游戏二进制和商店 DRM 不被剥离；后者是内核态的反作弊检测器。两者目标、权限、运行方式都不同。[R1][R3]
2. **Denuvo 的有效性来自“多层 + 每份拷贝绑定 + 把关键代码/常量藏进虚拟机和许可证”**，不是靠某一个不可破解的算法。它把逆向成本抬到“按作品逐个投入”的量级，从而保护首发销售窗口。[R1][R2][R6]
3. **它不是不可破**：校验逻辑最终运行在用户机器上；2026 年公开披露的 hypervisor 绕过（CVE-2026-105051）说明，攻击者可以在更底层伪造 CPUID/硬件环境，让上层校验“看到”一个合法机器。[R5][R9]
4. **对完全离线的本地工具，任何“防破解”都只能抬高门槛，不能从原理上阻止复制**：因为解密密钥、校验代码、数据最终都必须出现在用户机器上。真正收得住钱的是服务端价值（账号、云端数据、同步、持续更新、撤销权），不是本地壳。（本条为本文的工程判断，依据见 2.8 与第三部分，不是单一来源的结论。）
5. **本项目当前几乎没有防护面**：PyInstaller 分发包里前端 JS、JSON 数据、`tools/*.py` 源码都是明文；C# 宿主可被 .NET 反编译。要谈“D 加密式效果”，先得承认这一点。详见第二部分。

## 1. Denuvo 原理

### 1.1 两个产品不要混

| 维度 | Denuvo Anti-Tamper | Denuvo Anti-Cheat |
|---|---|---|
| 目标 | 防止游戏二进制被逆向、调试、篡改；保护商店 DRM 不被剥离 | 实时检测瞄准辅助、透视、地图外挂等作弊 |
| 运行位置 | 官方称**完全用户态**，不需要内核驱动 | 内核态驱动（ring 0） |
| 运行时机 | 游戏启动前介入，运行期持续校验 | 只在游戏运行、尤其是竞技模式时活跃 |
| 是否防作弊 | 官方明确说：**不防 mod，也不能阻止在受保护游戏里作弊** | 检测作弊，由发行商决定如何处置 |
| 是否防破解 | 提高逆向/调试/改内存的难度 | 不负责 DRM 防破解 |
| 联网 | 不要求永久在线；首次启动由平台要求在线，之后可离线 | 运行时会向厂商服务器发送 OS 与游戏的交互信息用于检测 |

这张表的关键结论：**不要把 Anti-Cheat 的内核驱动、隐私争议、蓝屏风险套到 Anti-Tamper 上**。公开讨论里最常见的混淆，就是把两者当成同一个东西。[R3]

### 1.2 它到底保护什么

Denuvo Anti-Tamper **本身不是商店 DRM**。官方定位是“工作在 Steam/Epic/Origin 等数字发行平台之上”，防止别人篡改或剥离游戏原有的授权校验。也就是说：

- Steam/Epic 负责“卖没卖、账号有没有权”；
- Denuvo 负责“不要让人轻易把这段校验拆掉、把游戏改成免授权版”。

官方给出的能力清单是：反逆向工程（含双虚拟机）、运行时代码/内存篡改检测、启动前环境完整性校验、代码加密、混淆、虚拟化、启动与运行期完整性验证、注入防护、虚拟机/hypervisor 检测、二进制重写（不需要源码，构建后处理）。[R1]

它不承诺“游戏永远不能被盗版”，承诺的是**显著提高破解的时间与人力成本**，尤其是发售后的前几周。

### 1.3 启动与授权流程（公开资料能确认的部分）

公开资料与官方说法可以拼出这样一条流程：

1. **首次启动必须在线**：游戏平台要求首次启动联网；Denuvo 利用这次连接重新校验游戏许可证。[R2]
2. **采集硬件指纹**：客户端收集 CPU、主板、BIOS、GPU、磁盘卷序列号、网卡、Windows 安装信息等多源标识，组合成一份设备指纹。公开技术分析列出的项很多，且会随版本变化。[R6][R7]
3. **向 Denuvo 服务端换许可证**：指纹被送到 Denuvo 服务器；服务端把指纹与预先从游戏中抽出的“隐藏常量”结合，生成许可证/令牌并返回本地保存。服务端具体算法没有公开。[R6][R7]
4. **后续启动离线校验**：官方明确说，后续启动不需要联网；只有游戏打了补丁、或硬件配置发生显著变化时，才需要再次联网。[R2]
5. **许可证与硬件绑定，但有更换额度**：公开的 Steam 端 EULA 摘要提到“24 小时内最多 5 台设备”，且每个名额有独立的 24 小时冷却计时；CPU/主板更换、关键 OS/BIOS 更新、游戏更新都可能改变指纹，被当作“新设备”占用下一个名额。[R5]
6. **“长期离线”不等于“对所有作品都完全离线”**：2021 年 11 月有公开报道称，Denuvo 自有域名到期导致多款近期游戏暂时无法启动。这说明部分作品/配置在启动时确实存在在线依赖，不能把“后续启动一定完全离线”当作对所有作品的保证。[R5][R36]
7. **不存在“所有作品固定周期心跳”的公开证据**：不同作品、不同平台策略可能不同。本文不把“每隔 X 天必须联网”写成普遍事实；这一点属于**公开资料不足**。

> 需要区分的说法：  
> - “首次在线激活”是**可以确认的**；  
> - “之后可离线”是**官方口径，且有条件**（补丁、硬件大改、个别作品的启动依赖除外）；  
> - “每隔 X 天必须联网一次”**没有找到普遍适用的公开证据**，不同作品可能不同；2021 年域名事件是“存在个别在线依赖”的旁证，不是“普遍周期复查”的证明。

### 1.4 核心技术机制

#### （1）二进制重写，而不是传统加壳

官方说它是“assembly-level integration post-build without a packer or wrapper”，即直接在编译后的 PE 二进制上做重写，不需要源码，也不需要外挂壳。官方给出的集成数据是：平均集成时间 <1 天，单次保护 5–10 分钟，已保护 758K+ 二进制、1,000+ 游戏（厂商自述）。[R1]

这和 VMProtect/Themida 那种“壳先拿到 CPU 再解密原程序”的模型不同：Denuvo 更像把原程序的一部分“挖掉”，换成自己的虚拟化代码和校验逻辑。

#### （2）代码虚拟化：把原生指令变成私有字节码

官方明确把“代码加密、混淆、虚拟化”列为三大手段，并提到“双虚拟机（dual virtual machines）”。[R1]

公开技术分析给出的机制层面描述是：

- 选中函数/基本块被转换成只有内嵌 VM 能理解的字节码；
- VM 带一套 handler 表与分发器（dispatch），把字节码翻译回等价语义；
- 原始常量/指令片段被抽走，运行时结合许可证数据还原；
- 大量使用混合布尔算术（MBA）、比特拆分/分散存储、等价指令替换、随机化，增加静态阅读难度；
- 双 VM 让分析者难以用一套 handler 覆盖全部虚拟化代码。

这些描述来自社区逆向分析，不是官方文档；官方只确认“虚拟化 + 双 VM”，不公开指令集与 handler 细节。[R1][R6][R7]

> **关于“控制流扁平化”**：这是商业壳常用的混淆手法，但公开的 Denuvo 专用分析更多描述为“虚拟化 + MBA + 常量抽取”，我没有找到直接称 Denuvo 使用控制流扁平化的权威资料。因此本文把它归为“同类技术”，不作为 Denuvo 已确认机制。

#### （3）按作品/按拷贝的许可证，而不是一个全局密钥

- **按作品/按构建**：每个受保护二进制抽出的常量、VM 结构可以不同；同一代保护也可能跨作品复用模板。
- **按拷贝**：许可证与设备指纹绑定；复制到另一台机器不能直接复用。
- **服务端参与**：服务端把指纹与隐藏常量混合，生成许可证；客户端只拿到结果，不掌握完整密钥体系。

公开分析能确认的是“许可证文件 + 硬件指纹 + 运行时解密”这条链路；**具体的密钥派生、签名算法、服务端混合方式没有公开**。[R6][R7]

#### （4）完整性校验、反调试、反注入

官方列出的能力包括：启动与运行期校验代码/数据、监控运行时内存篡改、阻止代码注入与未授权模块加载、检测虚拟化与 hypervisor 环境。[R1]

公开分析补充的机制细节包括：

- 对 VM handler 做 CRC/哈希校验，防止 handler 被替换；
- 在随机位置插入完整性检查，而不是只在入口查一次；
- 检测调试器、断点、内存补丁、模块替换；
- 对关键校验结果做分散存储，避免一个全局标志位被一次性改写。

这些手段的共同点是**把“单点校验”变成“多点、冗余、带副作用的校验”**，让破解者必须同时处理很多点，而不是改一个 `if`。

#### （5）代码/常量按需解密

官方说“code encryption”；同时官方辟谣“不会持续加密解密磁盘数据”，也就是说解密主要发生在内存/运行时，而不是反复读写硬盘。[R1][R2]

公开分析的说法是：被抽出的指令片段/常量在运行时按需还原；许可证里的数据被拆成多个值，参与解密与校验。**“整个代码段一次性解密”是不准确的简化**；更准确的说法是“关键片段/常量按需还原，配合 VM 执行”。

#### （6）水印：要区分两种东西

- **Anti-Tamper 的“每份拷贝绑定”**：许可证与设备/账号绑定，泄露的许可证可以被追溯。这是一种**取证式指纹**，不等于在可执行文件里嵌入可见水印。
- **Denuvo TraceMark**：这是另一个产品，把不可见水印嵌入游戏画面/视频，用来追溯截图、录像、泄露源的来源。[R16]

所以“每份拷贝的水印”要分开说：**代码/许可证层面是绑定与追溯；画面层面才是 TraceMark 的隐写水印**。公开资料没有证明 Anti-Tamper 会在代码里嵌入唯一水印。

### 1.5 为什么“有效，但不是不可破”

#### 有效的部分

1. **成本不对称**：破解一个 3A 作品需要投入数月人力，而保护方只需按作品付费；对发行商来说，只要撑过首发窗口就划算。
2. **每作品独立**：不同作品/不同保护版本的 VM 与常量不同，经验不能完全复用。
3. **多层冗余**：VM、完整性校验、反调试、许可证绑定互相牵制，拆一层不等于全拆。
4. **商业窗口**：Volckmann（Entertainment Computing，2024 年在线发表，卷 52）用数学模型并以评论数作为销量代理，估算“被破解时点”对收入的影响：若发售首周即被破，相对“未被破”情境的估计收入损失约 20%；若能撑过至少 12 周，之后即使被破，盗版对收入的影响也可忽略。研究明确说明：它衡量的是**破解时点的影响**，不等于“采用 Denuvo 比不发 DRM 净增收”，也没有证明盗版在所有情况下都伤害销量。[R13]

#### 不是不可破的部分

1. **校验逻辑在用户机器上**：这是原理性弱点。无论 VM 多复杂，最终要在这台机器上解密、执行、判断；攻击者可以调试、转储、打补丁。区别只是花多久。
2. **VM 不是不可逆**：学术上已有针对商用代码虚拟化（VMProtect、Themida、Code Virtualizer 等）的自动化/半自动化还原研究，证明“私有字节码 + handler”可以被分析。Denuvo 专用 VM 的完整公开还原方法我没有找到，但同类技术的结论是：VM 提高成本，不提供数学上的不可逆。[R19]
3. **环境可以被欺骗**：2026 年公开披露的 CVE-2026-105051 指出，Denuvo Anti-Tamper（截至 2026-03-04）可被通过 CPUID 拦截绕过 hypervisor 存在性检查（AMD 的 `SimpleSvm.sys`、Intel 的 `hyperkd.sys`/`hyperhv.dll`）。这不是“破解加密”，而是在更底层让校验看到一个假环境。[R9] 这正好说明：**只要判断发生在客户端，客户端环境就可以被伪造**。
4. **保护有生命周期**：发行商通常在首发窗口后停止付费、移除保护；一旦出现官方无保护版本，之前的努力就失去意义。2024 年研究的“12 周后影响可忽略”结论可支持“长期继续保护收益有限”的判断（这是据研究结论的推断，不是研究直接给出的商业建议）。[R13]
5. **性能争议反过来激励移除**：官方坚持“对合法玩家无影响”，但多家媒体/玩家测试在部分作品里发现移除 Denuvo 后帧时间改善（如《铁拳 7》《索尼克狂欢》《生化危机 8》等案例）。这使“破解/移除保护”除了免授权之外，还多了一个性能动机。[R5] 具体收益因作品、CPU、场景而异，不能一概而论。
6. **同代保护复用会加速沦陷**：公开报道显示，某些 Denuvo 版本在作品发售后数小时到数天内被攻破；这通常意味着某一代保护被研究透后，后续同代作品会更快。该因果是**推断**，公开资料没有给出逐作品的完整归因。[R10]

**一句话总结**：Denuvo 卖的不是“不可破”，而是“把破解成本推高到不划算，并覆盖最值钱的首发窗口”。这也是它商业上成立、技术上却不断被绕过的原因。

### 1.6 授权与商业条件

- **按作品授权**：官方定位是给发行商/开发商按 title 授权，构建后处理，不需要源码。[R1]
- **最终二进制交给对方处理**：官方明确“post-build binary-level integration without source access”。[R1]
- **成本不公开**：Denuvo/Irdeto 不公开报价。公开报道中较具体的一例是《孤岛危机 重制版》：Crytek 被报道为 12 个月支付 €140,000，之后每月 €2,000；若销量超过 50 万份另有 €60,000。该数字来自泄露合同/媒体报道，不是官方价目表。[R14][R15]
- **其他流传价格不可靠**：论坛里“$25,000/月 + $0.50/份”之类的说法没有可核查的一手来源，本文不采信为事实。[R5]
- **厂商自述规模**：1,000+ 游戏、758K+ 二进制、平均集成 <1 天、单次保护 5–10 分钟。[R1]
- **保护期通常与首发窗口绑定**：发行商会在首发期后移除；这也是“Denuvo 游戏后期变快/变干净”的常见原因。[R13]
- **法律手段也是商业模型的一部分**：2026 年 9 月 14 日，Denuvo 向美国加州北区联邦地区法院提交 DMCA 反规避投诉，指控匿名破解者 “voices38” 绕过至少 26 款游戏的 Anti-Tamper 保护，并试图通过其社交媒体账号查明身份。这说明厂商在技术之外还会用法律施压；信息来自 TorrentFreak 等媒体，未见法院文书原文。[R35]

### 1.7 查不到 / 只能推断的点

| 问题 | 结论 | 证据强度 |
|---|---|---|
| Denuvo 服务端如何把指纹与常量混合 | 未公开 | 官方/公开分析都只说“服务端处理”，细节未知 |
| 私有 VM 的完整指令集与 handler 语义 | 未公开 | 只有社区分析片段，无完整公开文档 |
| 是否所有作品都固定周期在线复核 | 没有普遍证据 | 官方说后续启动可离线；2021 年域名事件显示个别作品有启动期在线依赖 |
| Denuvo 官方价目 | 不公开 | 只有媒体报道/泄露合同 |
| Denuvo 专用 VM 的完整还原论文 | 未找到 | 只有同类商用 VM 的学术研究 |
| 大规模、跨作品的独立性能数据 | 不足 | 多为单作品测试，结论因配置而异 |

标注原则：本文把“官方确认”“媒体报道”“社区技术分析”“推断”分开写；没有一手来源的数字不当作事实。

### 1.8 哪些能借鉴，哪些不能

**可以借鉴的原理：**

1. **多层冗余**：不要只做一个 `if (licensed)`；把校验分散到多个模块、多个时机，并让它们互相依赖。
2. **每份拷贝绑定**：许可证与账号/设备绑定，至少能追溯泄露源。
3. **关键常量抽取**：不要把“是否会员”的判断和真实数据放在同一个明文 JSON 里；把高价值数据与许可证绑定。
4. **完整性校验**：对关键文件做签名/哈希清单，发现篡改时降级或要求重新授权。
5. **水印/指纹**：每份分发件带唯一标识，泄露可追溯（法律与商业威慑）。
6. **保护时间窗口**：把预算优先放在首发期，而不是追求“永久不可破”。

**不能直接照搬的：**

1. **自研 VM/控制流虚拟化**：工程量、性能开销、兼容性、维护成本都极高，不适合一个小型本地工具。
2. **按作品人工处理二进制**：Denuvo 有专职团队和 5–10 分钟的流水线；个人项目没有这个产能。
3. **内核反作弊**：和 DRM 无关，且会带来驱动签名、蓝屏、隐私信任问题。
4. **永久在线 DRM**：与“纯本地、离线可用”的产品定位冲突，会直接伤害用户体验。

**最值得借鉴的其实是商业策略**：Denuvo 的成功不只靠技术，而是靠“按作品收费 + 只保护最值钱的首发窗口 + 让破解成本高于收益”。对本地工具，应该把同样的思路用在“服务端价值”和“持续更新”上，而不是幻想把离线客户端做成不可破。

## 2. 这类思路里哪些我们能真的用上

> 本部分结合项目现状：Python 标准库 HTTP 服务 + 原生 JS 前端 + C#（.NET Framework 4.8 + WinForms + WebView2）桌面宿主；PyInstaller onedir 分发；纯本地、不读游戏进程、当前无账号/无联网校验。

### 2.0 先看清现状：当前分发包是“全透明”的

在讨论方案前，必须先承认本项目当前的实际防护面：

| 资产 | 当前形态 | 被获取的难度 | 说明 |
|---|---|---|---|
| 前端 JS/CSS/HTML | 明文随包 | 极低 | WebView2 通过本地 HTTP 加载，文件就在磁盘上 |
| 业务数据 JSON | 明文随包 | 极低 | `data/*.json`、`assets/*` 直接可读 |

### 2.2 商业壳与虚拟化：对 .NET 程序到底有没有用

**VMProtect** 官方现在明确支持 .NET 程序集：代码虚拟化、符号改名、内存保护、调试器检测、虚拟机检测、RSA 授权系统。个人版 Lite $399、Professional $599、Ultimate $999；公司版 $999/$1,499/$2,499，含一年更新。[R21]

但要注意三点：

1. **它保护的是“选中的方法/代码块”，不是整个应用的业务模型**。如果核心价值是明文 JSON 数据，壳再强也保护不了数据。
2. **.NET 虚拟化的兼容性风险高于原生**：反射、序列化、动态代理、WinForms 设计器、WebView2 互操作都可能受影响，必须做完整回归。
3. **壳本身也会被研究**：VMProtect 是公开可购买的工具，针对它的脱壳/还原研究长期存在；它提高门槛，不提供“不可逆”。

**Themida** 官方 FAQ 说得很直白：.NET EXE 可以保护，但“不如原生保护强”，因为 .NET 是解释型语言；VM/MUTATE 等保护宏对 .NET 不可用；**.NET DLL 不能保护**。[R22] 对本案（主逻辑在 Python/JS，C# 只是宿主）意义有限。

**Enigma Protector** 官方支持 .NET 文件、授权管理、代码混淆/变异/虚拟化。[R23] 能力与 Themida 类似，仍是壳级。

**.NET Reactor** 是最贴合 C# 宿主的低价选项：混淆、NecroBit、虚拟化、防篡改、硬件锁授权，官方标价 $249 起，支持 .NET Framework 4.8。[R24] 它不能保护 Python/JS，但能把宿主里的授权入口、密钥派生、进程校验做得更难读。

**Arxan/Digital.ai** 属于企业级应用加固，通常按项目/年报价，集成与维护成本高；对一个个人工具不划算。

**结论**：商业壳对“C# 宿主的授权入口”有中等价值，对“Python/JS/数据”帮助有限。**不要指望一个壳解决全部问题**；如果要做，选 .NET Reactor 或 VMProtect 之一，并把授权/解密核心集中到一个小而关键的 C# 模块里，而不是给整个程序加壳。

### 2.3 Python 侧：PyArmor、Nuitka、PyInstaller 的真实边界

**PyInstaller 不是保护工具。** 官方定义就是“收集脚本依赖 + 打包解释器”，产出可执行文件；它不混淆、不加密。公开的 PyInstaller 解包工具可以提取其中的 pyc，再用反编译/反汇编工具处理。[R25][R26] 单文件 exe 只是“运行时解压到临时目录”，更不是保护。

**PyArmor** 是 Python 侧最现实的选项：

- 支持过期时间（`-e`）、绑定设备、RFT/BCC/JIT 等模式；BCC 把函数转成 C 扩展；可与 PyInstaller 集成打包。[R27][R28]
- 官方明确承认边界：**“不擅长内存保护与反调试”**；如果 Python 解释器或 `pyarmor_runtime` 被替换/Hook，运行时数据仍可能被读取；官方建议配合代码签名、VMProtect 等外部工具保护解释器与 runtime。[R29]
- 价格：Basic $52、Pro $89、Group $158（一次性，按版本/条款）。[R30]

对本项目，PyArmor 的合理定位是：**让“直接读源码/pyc”的人多一道门槛**，尤其是把 `tools/*.py` 从明文源码变成混淆后的模块；但它挡不住“替换解释器 + Hook 运行时”的确定攻击者。

**Nuitka** 把 Python 编译成 C/原生二进制，标准版会保护源码结构，但官方自己说：**常量数据仍然可读**（密钥、文本、库用法等），需要商业版插件加密常量/数据，商业版 €250/年起。[R31] 因此：

- 标准 Nuitka：比 PyInstaller 难反编译，但字符串/常量仍可能暴露；
- Nuitka Commercial：可加密常量、嵌入数据文件、加密 traceback，但仍不是“不可逆”；
- 对依赖动态导入、`__file__`、资源路径的项目，编译改造有兼容性成本。

**结论**：Python 侧优先级是 **PyArmor（保护代码） + Nuitka（可选，提升反编译门槛） + 代码签名（保护运行时）**。不要用 PyInstaller 单文件当保护；它只是分发格式。

### 2.4 JS 侧：混淆只能防“随手看”，不能防“真想看”

前端 JS 在 WebView2 里运行，最终一定以可执行形式存在；DevTools、调试协议、内存 Hook 都能拿到运行时状态。混淆（字符串数组、控制流扁平化、死代码、自防御、VM 字节码）能显著增加阅读成本，但不能把逻辑变成秘密。[R32][R33]

可行策略：

1. **只混淆高价值/授权相关模块**，不要全站混淆（否则体积、性能、排障都变差）。
2. **把“是否会员”的判断从 JS 挪走**：JS 只负责展示，授权由宿主 C# 或服务端裁决；否则改一个 JS 变量就绕过。
3. **关键逻辑放 C# 宿主**：通过本地 HTTP API 或 WebView2 host object 暴露“结果”，而不是暴露“算法 + 密钥”。但 C# 仍可反编译，所以这只提升门槛，不改变原理。
4. **最终边界在服务端**：如果逻辑/数据必须保密，就不要下发；这是唯一在原理上成立的方案。

**结论**：JS 混淆适合“降低顺手复制/改代码”的概率，不适合作为收费的唯一防线。

### 2.5 授权校验：离线工具真正能做的那一套

#### 方案 A：激活码 + 离线签名校验（推荐做）

做法概述（不涉及破解）：

- 服务端用私钥对许可证 JSON 签名（Ed25519/ECDSA/RSA 均可），许可证包含：用户 ID、功能位、到期时间、设备指纹、签发时间、版本号；
- 客户端内置公钥，离线验证签名；签名通过才解锁功能；
- 私钥只保存在你的离线环境/服务端，绝不下发；
- 激活码可以是“许可证文件 + 短码”，短码用于人工输入/客服补发。

优点：

- 防 keygen：攻击者没有私钥，无法伪造合法许可证；
- 可离线：不需要每次启动联网；
- 可做功能分片、到期、试用、设备绑定；
- 成本低：Python 可用 `cryptography`/PyNaCl，C# 可用 `RSA`/`ECDsa`。

边界：

- 客户端里有公钥和校验代码，攻击者可以 patch 校验函数、替换公钥、或直接跳过解锁逻辑；
- 设备指纹可被虚拟机/模拟器伪造；
- 因此它**防伪造许可证，不防“把检查改掉”**。

#### 方案 B：机器指纹绑定

可用标识：CPU/主板/BIOS/磁盘卷序列号/网卡/Windows 安装 ID 等组合。要点：

- 不要用单一标识；用多源组合 + 容错（允许 1–2 项变化）；
- 换硬件/重装要有恢复流程（否则支持成本高）；
- 隐私政策要写清楚采集了什么、只用于授权、不上传原始标识（可上传哈希）；
- 虚拟机/沙箱/云电脑会误伤，需要白名单或人工申诉。

边界：指纹是“客户端自述”，hypervisor 可以伪造；2026 年 Denuvo 的 CVE 就是环境欺骗的实例。[R9]

#### 方案 C：在线心跳 + 定期复核

适合“有服务端”的阶段：

- 登录后发短生命周期 access token（如 15–60 分钟）+ refresh token；
- 服务端维护设备列表、并发上限、撤销列表；
- 客户端定期复核；离线时给 7–30 天宽限（加密缓存 + 本地签名）；
- 关键功能/数据每次向服务端取，服务端可随时停权。

边界：纯离线工具无法强制在线；宽限期缓存一旦下发就可能被复制；服务器故障会直接影响用户。

#### 方案 D：功能分片下发

把高价值功能/数据放在服务端，按权限下发：

- 云端行情、聚合统计、任务推荐、跨设备同步等；
- 客户端只拿“结果”，不拿“算法/全量数据”；
- 离线时只保留低价值缓存。

这是**原理上最有效**的方案，因为它改变了“价值存放位置”，而不是在客户端上和攻击者拔河。

### 2.6 完整性：代码签名、DLL 校验、防调试/反注入

**代码签名证书（Authenticode）**

- 作用：证明“这个 exe 是谁发布的”、签名后内容未被篡改；减少 SmartScreen/杀软警告。[R34]
- 不是：防破解。攻击者可以修改未签名副本，或 patch 已签名程序的运行时行为；签名只保护“静态文件完整性 + 发布者身份”。
- 成本：OV/EV 证书通常数百美元/年（以 CA 报价为准）；EV 还要硬件令牌/云签名。
- 对本案：**值得做**，因为能显著改善安装/信任体验，且是“完整性校验”的基础。

**DLL/资源哈希校验**

- 启动时校验关键文件哈希/签名，失败则降级/要求重新授权；
- 能发现“替换 DLL/改数据”，但校验代码本身可被 patch；
- 适合做“防误改/防注入”的卫生措施，不适合当收费主防线。

**.NET Framework 4.8 上的防调试/反注入**

- 可行 API：`Debugger.IsAttached`、`CheckRemoteDebuggerPresent`、进程/模块枚举、窗口标题检测等；
- 但托管代码可被 ILSpy/dnSpy 反编译，检查点容易被定位和 patch；
- 反注入（检测未签名模块、远程线程）能提高门槛，但会带来误报（覆盖层、输入法、杀软、无障碍工具）；
- .NET Framework 4.8 不支持 Native AOT；如果真要高强度，需把关键逻辑放到原生 C++ DLL，成本明显上升。

**结论**：完整性措施应做“低成本、可降级”的版本（签名 + 哈希清单 + 异常提示），不要做“检测到调试就崩溃/封号”的激进版本——会伤及正常用户和排障。

### 2.7 水印：能做，但要明确目的

可行做法：

- 许可证里带唯一用户 ID/构建 ID；
- 分发包里写入不可见标记（例如 JSON 字段顺序、空白/注释、资源文件哈希、隐藏的构建号）；
- 出现泄露时，用标记追溯来源；
- 对外说明“分发件包含唯一标识”，形成威慑。

边界：

- 标记可被剥离/重写；多个泄露源混合会污染；
- 误判会冤枉用户，必须有复核流程；
- 水印不防复制，只提高“分享后被追责”的概率。

**Denuvo TraceMark** 那类画面隐写水印不适合本项目（没有视频/截图分发场景），但“每份构建唯一标识 + 许可证追溯”的思路可以借鉴。[R16]

### 2.8 核心结论：完全离线的本地工具，天花板在哪里

**原理上挡不住的：**

1. **复制整个程序目录**：只要程序能在用户机器上独立运行，目录就可以被压缩、分享。
2. **Patch 授权判断**：校验代码、公钥、解密密钥都在客户端；攻击者可以改判断、换公钥、跳过解锁。
3. **提取明文/可解密数据**：离线可用的数据，最终必须能被客户端解密；运行时转储/内存 Hook 可以拿到。
4. **伪造设备指纹**：虚拟机/hypervisor 可以让客户端“看到”另一台机器；Denuvo 自己也被这种思路绕过。[R9]
5. **共享离线激活文件**：如果许可证不联网复核，复制许可证 + 模拟指纹就可能复用；在线复核只能提高成本，不能对纯离线强制。

**只能抬高门槛的：**

- 代码混淆/虚拟化/编译（PyArmor、Nuitka、VMProtect、.NET Reactor）；
- 加壳、反调试、反注入、完整性校验；
- 签名许可证、设备绑定、水印；
- 这些手段的真实价值是：**过滤掉“顺手改一改”的多数人，把确定攻击者的时间成本从几分钟抬到几小时/几天**。

**真正能改变力量对比的：**

- 把价值放到服务端：账号、权限、云端数据、跨设备同步、持续更新、撤销；
- 客户端只保留“低价值缓存 + 展示层”；
- 这样即使客户端被破解，攻击者得到的也只是一个空壳。

## 3. 落到建议

### 3.1 短期（几周内、成本可控）

按优先级排序：

1. **先修“明文源码随包”这个明显问题**
   - 当前构建脚本把 `tools/live_prices.py`、`r20_fetch_prices.py`、`installer.py` 作为明文数据加入包内，并通过 `--run-tool` 用 `runpy` 执行；
   - 这不是“防护强弱”问题，而是把源码直接送给用户；
   - 建议改为：这些脚本作为模块被主程序导入（冻结进 PyInstaller 的 pyc），或至少用 PyArmor 混淆后再随包；安装器/卸载器单独做原生小程序或受保护模块。
   - 注意：这会改动源码，属于后续实施项，不在本次调研范围内。

2. **加“签名许可证”**
   - 离线激活文件：用户 ID + 功能位 + 到期 + 设备指纹 + 版本号，服务端私钥签名；
   - 客户端公钥验签；解锁会员功能；
   - 成本低、可离线、能防 keygen；先做“防伪造”，不要追求“防 patch”。

3. **PyArmor 保护 Python 核心**
   - 先只保护 `launcher.py`/`serve.py` 的核心逻辑与授权模块；
   - 用 `-e` 做过期、绑设备；开 RFT（性能影响小）；BCC 按兼容性测试再上；
   - 与 PyInstaller 集成，避免把 `pyarmor_runtime` 暴露在可替换位置。

4. **C# 宿主加一层轻量保护**
   - 二选一：.NET Reactor（便宜、贴合）或 VMProtect（更强、更贵）；
   - 只保护授权入口、许可证解析、进程/模块校验，不要全量虚拟化；
   - 必做回归：WebView2 初始化、反射、序列化、安装/卸载、异常上报。

5. **前端只做“降低顺手改”的混淆**
   - 只混淆会员相关模块；不要全站混淆；
   - 授权判断不要放 JS；JS 只根据宿主返回的“已解锁”状态渲染。

6. **代码签名 + 哈希清单**
   - 给 exe/DLL 签名；构建时生成签名清单；
   - 启动校验关键文件；失败时提示“文件被修改，请重新安装”，而不是直接崩溃。

7. **每份分发件加唯一标记**
   - 许可证 ID/构建 ID 写入包内隐藏位置；
   - 客服与泄露追溯用；隐私政策说明。

**短期不要做的事**：自研 VM、内核驱动、全站 JS 混淆、把 JSON 全量加密但密钥放客户端、给 PyInstaller 加 UPX/壳（杀软误报和兼容性风险大于收益）。

### 3.2 中期（需要服务端配套）

1. **账号与设备管理**
   - 邮箱/第三方登录；设备列表；并发上限；撤销/封禁；
   - 短生命周期 access token + refresh token；
   - 离线宽限 7–30 天，宽限期内用本地签名缓存。

2. **授权服务**
   - 许可证签发/续期/换机/退款回收；
   - 功能位与版本绑定；灰度发布；
   - 服务端保留审计日志（谁、何时、哪台设备、哪个版本）。

3. **把高价值能力搬到服务端**
   - 实时行情/价格聚合；
   - 跨设备同步（设置、任务进度、配装、标注）；
   - 云端计算/推荐（不把算法和全量数据下发）；
   - 持续更新的数据包（签名 + 增量）。

4. **客户端瘦身**
   - 本地只保留 UI、缓存、离线基础数据；
   - 会员数据按需拉取，签名校验，短期缓存；
   - 这样即使客户端被破解，拿到的也只是缓存，不是完整产品。

5. **更新与完整性**
   - 签名 manifest；增量更新；回滚；
   - 服务端可下发“最低版本/强制更新”，应对泄露版本。

6. **支付与合规**
   - 支付渠道、发票/退款、隐私政策、用户协议；
   - 若涉及海外用户，注意税务与数据合规。

### 3.3 不建议做（投入大、收益低、或明显伤体验）

1. **自研 Denuvo 式 VM/控制流虚拟化**：工程量巨大、性能开销高、兼容性差、维护无底洞；对一个本地地图工具，投入产出比极低。
2. **内核驱动/反作弊**：与 DRM 无关；驱动签名、蓝屏、隐私信任、杀软冲突，都会伤害用户。
3. **永久在线 DRM**：与“纯本地、离线可用”的核心卖点冲突；网络故障/服务器维护会直接导致用户无法使用。
4. **激进反调试**：检测到调试就崩溃/封号；会误伤开发者、客服、无障碍工具和杀软，修复成本高。
5. **把全部 JSON 加密、密钥硬编码在客户端**：只是把明文换成“运行时明文”，确定攻击者仍可转储；投入不小，收益有限。
6. **全站 JS 混淆/VM 混淆**：体积、性能、调试、CSP 兼容性都会变差；对确定攻击者无效。
7. **给 PyInstaller 产物套 UPX/通用壳**：杀软误报率高、启动慢、可能破坏 WebView2/子进程；收益远小于麻烦。
8. **依赖单一商业壳解决所有问题**：壳保护不了明文数据、服务端价值和用户体验；还会带来许可费与兼容性负担。
9. **对免费用户做硬件锁**：支持成本、隐私反感、口碑损失；免费版应尽量无摩擦。

### 3.4 商业模型：哪些价值放服务端才收得住钱

| 价值类型 | 放本地 | 放服务端 | 判断 |
|---|---|---|---|
| 静态地图/物品/任务数据 | 必然会被复制 | 可作为基础免费内容 | 本地放基础版，服务端放“最新/独家” |
| 实时行情/价格 | 抓取逻辑和数据都可被提取 | 服务端聚合、按权限下发 | **必须服务端**，否则等于白送 |
| 计算/推荐/规划 | 算法在客户端可被逆向 | 服务端算，客户端只拿结果 | 高价值计算放服务端 |
| 跨设备同步 | 本地文件可被复制 | 账号 + 云存储 | 服务端天然收费点 |
| 持续更新 | 离线包可被分享 | 签名增量 + 权限 | 订阅制的核心 |
| 账号/身份/社区 | 本地无法验证 | 服务端 | 服务端 |
| UI/皮肤/单机功能 | 本地 | 本地 | 可做一次性买断，别指望防复制 |
| 离线基础功能 | 本地 | — | 免费引流，不加密 |

**商业结论**：

- **本地能收费的**：一次性买断的“离线增强包”、皮肤、单机高级功能——但要接受“会被分享”，靠价格和更新节奏而不是 DRM。
- **服务端才能收住的**：实时数据、云端同步、跨设备、持续更新、账号权益、社区/交易。
- **最划算的组合**：免费本地基础版（引流） + 订阅云端增强（持续收入） + 一次性买断的离线增强（低支持成本）。
- **不要用 Denuvo 的成本结构**：Denuvo 按作品收 €140k/年级别，本项目全年收入可能都覆盖不了；用“签名许可证 + 服务端权益”的轻量方案更合理。

### 3.5 推荐路线图（按投入产出排序）

**第 1 阶段（1–2 周，低风险）**
- 移除明文 `tools/*.py` 随包；
- 加签名许可证（离线验签 + 功能位 + 到期 + 设备指纹）；
- 代码签名；
- 会员相关 JS 轻量混淆；
- 前端授权判断改为“宿主/服务端裁决”。

**第 2 阶段（3–6 周，中等风险）**
- PyArmor 保护 Python 核心；
- .NET Reactor 或 VMProtect 保护 C# 授权入口；
- 哈希清单 + 启动完整性校验；
- 每份构建唯一标记 + 追溯流程；
- 设备换机/恢复流程与客服工具。

**第 3 阶段（服务端上线后）**
- 账号/设备/权益服务；
- 实时数据与云端同步；
- 签名增量更新；
- 离线宽限与撤销；
- 支付/合规/隐私。

**如果只能做一件事**：**把高价值能力搬到服务端，并给本地客户端加“签名许可证 + 明文源码清理”**。这比任何壳都更能改变投入产出比。

## 4. 风险与合规提醒

1. **不要研究/复现破解步骤**：本文只引用公开原理与漏洞描述；任何绕过、patch、脱壳操作都不在范围内。
2. **不要把“防破解”写成“绝对安全”**：对用户和合作方都应说明“提高门槛，不保证不可破”。
3. **隐私**：设备指纹、硬件标识、行为日志都可能涉及个人信息；采集前要说明目的、范围、保留期，尽量本地哈希、最小化上传。
4. **杀软误报**：加壳/虚拟化/反调试是杀软敏感行为；上线前要做多引擎扫描与白名单沟通。
5. **许可证服务器可用性**：如果做在线复核，必须有降级/宽限/故障预案；否则一次宕机就会变成口碑事故。
6. **开源/第三方许可**：PyArmor、Nuitka、VMProtect、.NET Reactor 的授权条款不同；商用前确认是否允许闭源分发、是否按版本/按公司收费。
7. **法律**：水印追溯、封禁、退款、用户协议要配套；不要用“怀疑即封”的策略。

## 附录 A：术语表

- **Anti-Tamper**：反篡改，保护二进制/内存/授权逻辑不被修改。
- **Anti-Cheat**：反作弊，检测多人游戏中的外挂行为。
- **DRM**：数字版权管理，负责“有没有权/卖没卖”。
- **VM（此处）**：代码虚拟化，不是虚拟机软件；把原生指令转成私有字节码并用内嵌解释器执行。
- **Handler**：VM 中负责解释某类字节码指令的处理函数。
- **MBA**：混合布尔算术，用等价的算术/位运算表达式混淆逻辑。
- **设备指纹**：由多个硬件/系统标识组合成的设备标识。
- **离线签名许可证**：服务端私钥签名、客户端公钥验签的授权文件。
- **水印**：嵌入分发件/画面的唯一标识，用于追溯泄露源。
