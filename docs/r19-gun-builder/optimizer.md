# R19 自动配枪（优化器）：算法、约束与限制

实现位置：`gun_builder.js` 的 `optimize()`。界面入口：属性面板下方的「优化建议」
（本轮先做成可调用能力 + 单测覆盖，UI 尚未挂按钮，见 §6）。

---

## 1. 为什么不是穷举

一把 M4A1 的合法装配组合是 10^8 量级（18 个槽位 × 平均 5~40 个候选 × 递归子槽）。
浏览器里不可能全枚举，也不能让页面卡死。

实测参考站的 `FORGE` 面板也是异步生成（按钮文案是
*"Press GENERATE BUILDS to compute the 3D Pareto frontier"*），说明它同样有计算预算。

本实现的目标是**在固定预算内给出可安装的改进方案**，而不是宣称找到全局最优。

---

## 2. 算法

```
for each 权重组合 w in WEIGHTS:            ← 4 组预设权重
    cur = sanitize(当前装配)                 ← 非法项先清掉
    best = score(cur, w)
    for round in 1..3:                      ← 最多 3 轮局部改进
        for path in 该装配的槽位树（前序遍历）:
            for cand in 该槽位的合法候选:
                若 cand 被 blockIds 禁掉 → 跳过
                trial = 装上 cand → sanitize（父件变了子槽会自动清）
                若 maxCost 且 trial 成本超预算 → 跳过
                if score(trial, w) < best:  ← 越小越好
                    记下这个 cand 与本轮最优
        if 本轮没有改进 → break
    输出 { name, installed, stats, cost, score }
```

关键点：

1. **每次试装都过 `sanitize`**：换护木会让旧导轨失效，这一步把不合法的子件清掉，
   所以产出的方案一定是"当前兼容关系下可安装"的，不存在虚构的组合。
2. **预算按评估次数计**（默认 4000 次），不是按时间 —— 结果可复现，不受机器快慢影响。
3. **权重不同 → 方案不同**，天然产出多套候选（去重后通常 2~4 套）。

---

## 3. 目标函数（越小越好）

```
score =   w.recoil × (recoilV + recoilH) / 100
        − w.ergo   × ergonomics / 50
        + w.weight × weight / 5
        + w.cost   × (cost / 200000)      ← 预留，当前四组权重里 cost 只在「性价比」启用
```

除以 100 / 50 / 5 是为了把三个量纲拉到同一数量级，否则后坐力（几百）会完全压过
ergonomics（几十）与重量（几公斤）。

四组预设权重：

| 名称 | recoil | ergo | weight | cost |
|---|---|---|---|---|
| 低后坐力 | 1.0 | 0.15 | 0.1 | 0 |
| 高人机工效 | 0.15 | 1.0 | 0.1 | 0 |
| 轻量化 | 0.2 | 0.2 | 1.0 | 0 |
| 性价比 | 0.4 | 0.4 | 0.2 | 1.0 |

> 权重是**启发式**，没有官方依据。写在这里是为了让用户能评判这个优化器在优化什么，
> 而不是把它当成"游戏内最优解"。

## 4. 约束

| 约束 | 实现 |
|---|---|
| 只能装该槽位 `allow` 里的件 | 候选来自 `candidates()`，与手动装配同一套规则 |
| 互斥件不能共存 | `sanitize()` 里通过 `validate()` 拦掉 |
| 父件换了子件要清 | `sanitize()` 反复清理，最多 12 轮 |
| 可选预算上限 | `opts.maxCost`，超预算的 trial 直接丢弃 |
| 可选禁装清单 | `opts.blockIds`（对应参考站的 `BLOCKED`） |
| 计算预算 | `opts.budget`（默认 4000 次评估） |

**没有实现**的参考站约束：`FORCED`（强制包含某件）、`MAGS`（弹匣容量档位）、
`SCOPE`（近/中/远瞄具）、`TACTICAL`（战术设备必装）、`SUPPRESSED`（消音）。
它们在参考站是生成器的输入参数，本轮没做进优化器。

## 5. 实测表现

单测（`node tests/js/gun_builder_test.js`）对 AK-74 空装配跑默认权重：

| 指标 | 结果 |
|---|---|
| 产出方案数 | ≥ 2（去重后） |
| 评估次数 | ≤ 2500（预算内） |
| 耗时 | < 8 s（实测通常在 1 s 内） |
| 方案合法性 | 全部通过 `validate()` |
| 后坐力 | 全部不劣于空装配 |

## 6. 当前的边界（必须如实说明）

1. **UI 入口还没挂**：`optimize()` 已实现并有单测覆盖，但配枪页还没有"一键优化"按钮。
   本轮的时间优先给了"属性计算 + 兼容 + 预设 + 比较"这条主链。
2. **不是 Pareto 前沿**：参考站宣称算的是 3D Pareto frontier；本地是"多权重贪心 + 局部改进"，
   只保证"在预算内找到更优解"，不保证前沿完整性。
3. **不处理瞄具/枪口的组合语义**：优化器把每个槽位当独立维度，
   不会主动去找"某个倍率瞄具 + 对应安装座"的成套方案。
   `chains()` 提供了按安装链生成候选的能力（见 §7），但没有接进优化器。
4. **没有缓存**：每次调用重新算。当前耗时在可接受范围内，所以没做跨调用缓存。

## 7. 附：安装链生成 `chains()`

给"枪口组合 / 瞄具+座+导轨"这类多级安装用的辅助函数：

- 遍历树上的每个槽位 → 取该槽位的合法候选；
- 如果候选自己还有子槽（例如瞄具座），就把它的第一个可用子件也拼进链里；
- 输出 `{ root, sid, label, chain: [{path, id, n}, ...] }`。

这样"某个瞄具 + 它需要的安装座"是一条链，而不是两个独立下拉。
它只负责**生成候选链**，真正应用仍走 `validate + sanitize`，不会绕过兼容性。
