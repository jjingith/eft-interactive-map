## 4. SHA-256 契约与调用链

### 4.1 三种"哈希/大小"对象必须区分（回答问题 2、3）

| 对象 | 位置 | 语义 | 生成点 | 是否被验证 |
|---|---|---|---|---|
| 上游响应哈希 | `sources[].sha256` | **抓取时上游 HTTP 响应字节**的 sha256 | `fetch_data.py:981`（`hashlib.sha256(raw)`，`source_entry` :975–983） | 否——离线不可重验，校验器只查格式 |
| 本地文件大小快照 | `items/gunslots/gunPresets.bytes` | 落盘文件**生成时刻**的 `stat().st_size` | `fetch_data.py:2085/2096/2099` | 是——校验器 C5 比对当前大小，漂移报 warning |
| 本地文件 SHA-256 | **不存在** | — | — | — |
| 资产文件哈希 | `sources[6/7]`（图标类） | 下载图标/自绘 SVG 的**文件字节**哈希 | `fetch_data.py:1953/1975` | 否——无消费者比对 |

**结论（问题 2）**：`meta.sources[].sha256` = **上游原始响应**（"保存了上游哈希"）；
`meta.*.bytes` = **本地生成文件大小**。项目**从未验证过任何本地文件哈希**——
两者不能互相替代，当前也不存在可替代的对象。**代码已证实**。

**结论（问题 1）**：当前机制对"意外修改/损坏/替换"的识别能力**非常有限**：
- 能发现：JSON 解析失败、顶层类型错误、文件缺失、bytes 漂移（仅 warning）——
  且仅当有人主动运行 `r20_validate_data.py` 时（无自动门禁）。**代码已证实**。
- 不能发现：内容被改但字节数恰好不变的修改；字节变化但无人跑校验器的修改；
  校验器本身无法区分"合法更新后的漂移"与"意外篡改"（两者都表现为 bytes 不一致）。
  **静态推断**（由 bytes-only 契约直接推出）。

**问题 3 的区分方法（现状 vs 应然）**：现状无法区分三者，只有"bytes 一致/不一致"。
应然区分见 §10：合法更新 = 同步更新哈希记录；意外篡改 = 哈希不匹配且无更新记录；
数据损坏 = 解析失败；历史差异 = 有备份/时间戳可对照。

## 5. 数据更新、写入和回滚流程（问题 4、5）

### 5.1 写盘机制

- `fetch_data.py:968–973` `write_atomic`：**先写 `<name>.tmp` 再 `os.replace`**，
  文档字符串明言"避免半截文件覆盖掉可用数据"。全部业务 JSON（items :2058、gunslots :2061、
  gun-presets :2075、maps :2374、meta :2206/:2375）均经此路径。**代码已证实**。
- 序列化格式：`ensure_ascii=False, separators=(",", ":")`（紧凑）；meta 用 `indent=1`。
  **代码已证实**。
- 解析顺序：上游数据先 `json.loads` 进内存变换，构建完整 payload 后才落盘——
  **解析在写入之前**；但**没有结构校验门禁**（无 schema 校验步骤）。**代码已证实**。
- 写入顺序（items 阶段 :2058→2061→2075→2206）：**业务 JSON 先、meta 后**；
  地图阶段 :2374 maps.json → :2375 meta.json 同序。**代码已证实**。

### 5.2 中途失败的后果（问题 4、5 的直接回答）

- **单文件层面**：`os.replace` 在 Windows/NTFS 上是原子的——原文件要么完整保留、
  要么被完整替换，**不存在半截文件**。**代码已证实**（机制）+ 平台语义 **静态推断**。
- **多文件层面**：**没有事务**。若在 :2058（items 写完）与 :2206（meta 写完）之间中断，
  会留下 **新 items.json + 旧 meta.json**（以及旧 gunslots——若中断更早则相反的混杂）。
  **代码已证实**（写入顺序）+ **静态推断**（中断窗口后果）。
- **现实世界的混杂证据**：meta 停在 2026-10-20，而 gunslots.json 与
  `items.json.r1921.bak.json` 的 mtime 同为 2026-10-27 20:13:31（同批次写入），
  meta 未随之更新。gunslots.json 的**唯一写者是 fetch_data.py:2061**（**代码已证实**，
  全 tools 扫描无第二写者），而 fetch_data 所有正常路径结尾都会写 meta——
  因此最可能是**一次更新在 meta 写入前中断**，或走了未覆盖 meta 的非常规入口。
  **静态推断**（无当日运行日志，**未验证**）。
- **更新后的旁路修改**：`r1926_datafix.py:51–53`（tmp+replace，`indent=1`，不更新 meta，
  一次性备份 `items.json.r1918.bak.json` :22）与 `r1929_datafix.py:89–92`（tmp+replace，
  紧凑格式，不更新 meta，一次性备份 `items.json.r1921.bak.json` :49）都会**原地改写
  items.json 而不触碰 meta**——bytes 漂移的直接根源。**代码已证实**。

### 5.3 备份与回滚（问题 5）

- `fetch_data.py` 全文**无 backup/rollback/restore 逻辑**（关键词扫描为空）。**代码已证实**。
- 现有 9 个 `data/*.bak.json / *.prev.json` 是**各轮次手动/脚本一次性备份**（如
  r1926/r1929 的一次性 bak，只备不覆盖），**没有统一命名、保留策略或回滚工具**。
  **代码已证实**（脚本内）+ **静态推断**（无自动化）。
- **结论**：不存在"可靠回滚路径"。单文件损坏可由 `os.replace` 免除；但
  **多文件版本混杂没有任何自动恢复手段**，只能靠手动比对 bak/重跑 fetch_data。
  不得声称系统具备回滚能力。**代码已证实**。

## 9. 三种改造方案比较

### 方案 A：只记录本地文件 SHA-256
- 做法：`fetch_data.py` 落盘后对每个业务 JSON 计算 sha256 写入 `meta.<block>.sha256`；
  校验器 C5 比对（现有"若有 sha256 则比对"分支已支持）。
- 优点：最小改动（meta +1 字段/块，fetch_data +1 赋值，校验器零改动）；能定性
  "意外篡改 vs 合法更新"（合法更新=哈希随 meta 同步刷新）；向后兼容（旧 meta 无字段时
  校验器降级 warning，已实现）。
- 缺点：仍无法区分"合法更新没记哈希"与"篡改"（需配合 R2 纪律）；对上游漂移不可见。

### 方案 B：同时记录上游与本地 SHA-256
- 做法：保留 `sources[].sha256`（**本来就是上游哈希**），叠加方案 A 的本地哈希。
- 优点：**几乎免费**——上游哈希已存在，增量=A；两层漂移可分别归因（上游变了 vs 本地被改）；
  解析/规范化后两哈希天然不同，分字段存放即无误报。
- 缺点：上游哈希仍不可离线重验（需联网轮次）；字段解释需文档固化（本文档即证据）。

### 方案 C：先暂存、验证，再发布
- 做法：全流程产物写 staging 目录 → 解析+结构校验 → 成功后逐文件 `os.replace` 发布，
  **meta 最后替换**。
- 优点：把 §5.2 的中断窗口收敛为"要么旧整套、要么新整套+旧 meta（可检测）"；
  校验失败不触碰正式数据。
- 缺点/边界：多文件替换**并非天然事务**（Windows 无跨文件原子操作）——只能靠
  "meta 最后写 + 发布后立刻跑校验器"逼近；需要目录切换/清理规则；对现有调用方式
  （直接写 `data/`）改动面大于 A/B；临时目录在崩溃后的残留清理需设计。
- 兼容性：对离线运行与消费者无影响（消费路径不变）；对 datafix 类脚本需同样接入。

## 10. 推荐的最小改造方案（问题 6）

**推荐：A+B 合并态 + C 的轻量纪律**（不引入完整 staging 目录作为第一步）：

1. **本地哈希契约（A）**：`meta.items/gunslots/gunPresets` 各增 `sha256`（落盘文件哈希，
   在 `fetch_data.py:2085/2096/2099` 处一并计算）；`sources[].sha256` 语义保持上游不变（B
   即告成立，无需新字段）。
2. **写者纪律（消 R2）**：`r1926_datafix.py` / `r1929_datafix.py` 改写数据后必须同步更新
   meta 的 `bytes/sha256`（或提供 `--check` 模式由调用方决定）；**最小实现**＝重写后
   stat+hash 并以 write_atomic 回写 meta 对应字段。
3. **门禁（消 R5）**：更新流程结尾与测试收集阶段调用 `r20_validate_data.py`（只读，零风险）；
   C5 已支持 sha256 比对，仅需把"bytes 漂移 warning"升级为"sha 不匹配 error"的优先级语义
   （bytes 漂移仍保持 warning，兼容历史）。
4. **暂不实施完整 C**：写序"meta 最后"已具备（§5.1）；staging 目录作为第二批（当出现
   频繁多文件混杂时再上）。

改动面：`fetch_data.py`（3 处赋值）、`r1926_datafix.py`/`r1929_datafix.py`（各 +5 行）、
`r20_validate_data.py`（C5 文档级微调）、`meta.json` schema+1 可选字段（向后兼容）。
**不涉及** app.js、旧测试、业务语义。

## 附：六个审计问题的直接结论

1. **能否识别意外修改/损坏/替换？** 仅能识别"解析失败/顶层损坏/缺文件/bytes 漂移（warning）"，
   且须人工跑校验器；**内容级篡改（保字节）完全不可识别**（R1）。
2. **meta 的 SHA-256 是什么？** `sources[].sha256` = **上游原始响应**；业务文件引用块
   只有**本地文件大小快照**，无哈希。**代码已证实**。
3. **漂移/不匹配/合法更新如何区分？** 现状无法区分；需 §10 的本地哈希契约。
4. **更新中是否可能不一致？** **是**——写序窗口（items 新 / meta 旧）+ datafix 旁路改写，
   且有现实证据（meta 10-20 vs gunslots 10-27）。
5. **中途失败能否保住原数据？** 单文件能（`os.replace` 原子）；**多文件不能**（无事务、
   无回滚）。
6. **最小改造范围？** §10：A+B 合并态（本地哈希 + 既有上游哈希）+ 写者纪律 + 校验门禁；
   改 4 个工具文件 + meta 可选字段，不碰 app.js 与旧测试。
