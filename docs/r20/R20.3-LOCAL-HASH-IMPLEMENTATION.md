## 3. 本地哈希契约与字段位置

```
data/meta.json
├─ sources[i].sha256          ← 上游响应字节哈希（既有，语义未变）
└─ items.sha256               ← 本地文件哈希（R20.3 新增）
   gunslots.sha256
   gunPresets.sha256
```

写入点（`tools/fetch_data.py`）：`items_bytes` / `gunslots_bytes` / `gun_presets_bytes`
三个**最终落盘字节变量**；`bytes = len(变量)`、`sha256 = hashlib.sha256(变量).hexdigest()`。
**代码已证实**：两者取自同一份字节，满足"bytes 与 sha256 描述同一文件内容"。

## 4. `meta.schema` 是否升级：**不升级**，依据如下

- `meta.schema` 的写入值是 `fetch_data.py:50` 的 `SCHEMA = 8`，其上方注释逐条描述的是
  **地图数据内容/图层代次**（"8 = 高级资源点再收录「情报文件夹」…"），并同时写入
  `maps.json`（`:2344`）与 `meta.json`（`:2337`）——**它表示数据代次，不是元数据结构版本**。
  `ITEMS_SCHEMA = 6`（`:69`）注释明写"与地图 SCHEMA 各自独立"。**代码已证实**。
- 硬编码消费者：`tests/test_fetch_data.py:856` 断言 `meta["schema"] == data["schema"] == fd.SCHEMA`
  （maps.json 的 schema 实测为 8）。升版将迫使**同时改 maps.json（业务数据，本轮禁止）**，
  并使该旧断言失败（不得改旧测试）。**代码已证实**。
- 无任何代码对 meta 整体做严格相等比较（`grep "meta =="` 无命中）；`app.js` 只 `loadJSON`
  后展示，不读 `meta.schema`（`:343/:650/:655/:678`）。**代码已证实**。
- 结论：新增字段是**可选扩展**，不改变数据代次语义 → **不升版**。若将来需要升版，
  应由"业务数据代次变化"驱动（连同 maps.json 与 SCHEMA 一起），而不是元数据加字段。

## 5. 本地哈希 vs 上游响应哈希

| | 上游响应哈希 | 本地文件哈希 |
|---|---|---|
| 位置 | `meta.sources[].sha256` | `meta.{items,gunslots,gunPresets}.sha256` |
| 对象 | 抓取时上游 HTTP 响应字节 | 最终落盘的业务 JSON 文件字节 |
| 生成 | `fetch_data.py:981`（`hashlib.sha256(raw)`） | `fetch_data.py` 新增：落盘字节变量 |
| 可离线重验 | **否**（需重新下载） | **是**（校验器 C5 直接比对磁盘文件） |
| 语义 | 上游数据是否变化 | 本地文件是否变化 |

**代码已证实**：两者互不替代、互不覆盖语义；`sources[]` 的含义本轮一字未改
（`test_r20_3_hash_contract.py::test_upstream_sources_semantics_unchanged` 断言之）。

4. `meta.*.bytes` **保持原值未改写**（按任务书要求），因此 bytes 与 sha256 目前分别指向

## 7. 校验器状态语义（R20.1 契约保持不变）

`pass` / `warning` / `fail` / `skipped` 定义未变；汇总：有 error → fail（退出码 1），
仅 warning → pass（退出码 0，warnings 保留）。本轮新增两条映射：

- C5 **缺 sha256** → `warning`（"未完成哈希验证"），不得静默当作已验证；
- C5 **sha256 格式非法** → `error` → check `fail` → 退出码非零。

§七 表格逐项落地（**测试已证实**，见 §8）：

| 场景 | 结果 |
|---|---|
| 哈希匹配 | C5 `pass`，退出 0 |
| 内容被改（哈希不匹配） | error + 整体 `fail` + 退出 1 |
| 文件缺失 | error + `fail` + 退出 1 |
| 哈希字段缺失 | `warning`，**不宣称已验证**，退出 0 |
| 哈希格式非法 | error + `fail` + 退出 1 |
| bytes 漂移但哈希匹配 | 哈希 `pass`（明细含"sha256 一致"），bytes `warning` 保留，退出 0 |
| bytes 漂移且哈希不匹配 | **error 优先**，整体 `fail`，退出 1 |
| 内容被改但字节数不变 | **由 SHA-256 检出**（bytes 无漂移 → 无 bytes 警告，仅哈希 error） |

## 12. 尚未解决的问题与建议下一步

1. **旧 datafix 脚本不更新 meta**（`r1926_datafix.py` / `r1929_datafix.py`）：一旦它们再次改动
   `items.json`，校验器会报 **sha256 不匹配（error）**。这是**有意的暴露**；
   正确处置是让脚本同步更新 meta（或改走统一生成流程），**不是自动刷新哈希掩盖问题**。
   本轮按 §十 明确不改这两个脚本。→ 建议下一轮专项审议。
2. **14 个业务文件仍无本地哈希**（maps/ammo/bosses/…）：建议按"更新频率 × 体积 × 校验价值"
   排优先级分批纳入，首批建议 `maps.json`（地图数据体量大、变更少）。
3. **`bytes` 语义仍是"生成时刻快照"**：与 sha256 存在时间点差异。建议后续把 bytes 明确定义为
   "记录时刻文件大小"，或改为记录 sha256 所在时刻的 bytes（需重跑一次生成流程，本轮禁止）。
4. **meta.json 的 bytes/hash 不一致场景无标准处置流程**：建议下一轮定"漂移+哈希一致"的处置规范
   （更新 meta / 记入审计报告 / 视为合法更新）。
5. **R20.2 审计的其余风险**（无回滚机制、多文件无事务、多写者收敛、许可核实）本轮均未处理，
   仍以 R20.2 报告为准。
