# R236 · 整图分块识别（修「只能识别出几个物体」）

## 用户原话（2026-11-11 14:37）

> 「你再看看 小喵工具箱是怎么做的 我现在试了几次都不对 只能识别出几个物体」

## 根因（三段实验定位）

1. **整图单次 det 把小字压没了**：1080p 截图走 det（960 边长）缩放 0.5，游戏
   14px 名字变 ~7px，检测器基本失明——只有最大号的几行能出框。
2. XiaoMeow 的答案在 R32 报告 §3.4 里本来就有：`RecognizeChunked` 把大图切成
   **256px 块**逐块识别（每块原生分辨率 + OcrPreprocess ≤1.6× 放大），坐标按
   `(x*scale + tileX)` 映射回全图——R234 明确标注「未复刻」，这就是差距。
3. 用 MCP 重开 `XiaoMeowToolbox.dll`/`.Core.dll` 复核了 TilePlan/RecognizeChunked
   参数与 PriceScanner 的 ROI 用法（游标为中心的小区域，重叠 0 也够）。

## 实现（tools/ocr.py）

- `recognize()` 分流：最长边 ≤ `TILED_TRIGGER(1200)` 走原单次直识；超过走
  `_recognize_tiled`。
- **块几何**：块 640 / 步进 320（`TILE_OVERLAP=0.5`）。关键推导：窗口每 step
  平移一次，文本宽 L 完整落入某块 ⇔ **L ≤ W − S**。整页库存里物品名最宽约
  320px（16px 字号 × 20 字），640/320 恰好保证；1080p 约 24 块 ≈ **6s**，1440p
  约 40 块。块数超 `TILE_MAX_COUNT(400)` 退回无重叠网格（保险丝）。
  - 期间踩了一个单位坑：TilePlan 的 overlap 是**比例**，首版写成 64px，
    `256*(1-64)` 为负 → step 退化成 1 → 137 万块跑 7 分钟被超时杀掉。
- **跨块去重 `_dedup_lines`**：同文（去空格子串/相似 >0.75）且（中心距 <24px
  **或** 框 IoU>0.3）只留最高分。IoU 是为「重叠块里同段文字被切出部分框 vs
  完整框」准备的——两框中心能差几十像素但 IoU 很高（实测 Flyye MBSS 同名两行）。
- **匹配器两处修复**（均有单测）：
  1. token 层候选窗口原来只对 `len(tok)` 开档，全名键带空格进不了候选 → OCR
     吞空格时 **MP-133 错配 MP-153**。修：对 `len(tok)` 与 `len(tok 去空格)`
     各开一档；ratio 对键的两种形态取较高（`_ratio_best`）。
  2. ≤6 字符 token 在 0.60 阈值下太松（HUD 文字 `Esape` 擦线配上 `eagle`）。
     修：去空格后 ≤6 用 0.72，>6 用 0.60（规格阈值只在长 token 上保留）。

## 效果（1920×1080 库存风合成图，12 个真实物品名 + 价格标签）

| 阶段 | 结果 |
| --- | --- |
| R234 旧行为（单次直识） | 25 行 / 11 命中（真实游戏截图上更差，即用户所见） |
| R236 分块首版（256/0.25→64px 重叠） | 名字被块缝切断，MP-133 漏 |
| R236 分块（640/0.5）+ IoU 去重 + 匹配器修复 | **25 行 / 12 命中 12/12，6.4s，零误报、同名重复清零** |

## 边界（如实）

- 分块是**串行**推理，4K 截图（3840×2160）约 80 块 ≈ 25s，可接受但未做并行/
  Web Worker 化；TILE_MAX_COUNT 保险丝只加大步进不裁剪。
- 真实游戏截图（仓库/跳蚤 UI）的实测命中率仍待用户进游戏验证——合成图字体
  与游戏渲染有差异，但管线瓶颈（分辨率）已消除。
- XiaoMeow 的 overlap=0 在它的 ROI 用法下成立；我们的 0.5 是整页用法的必要
  修正（有几何推导与实测背书），已在常量注释里说明。
