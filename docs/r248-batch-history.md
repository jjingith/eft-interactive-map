# R248 修「改 ShareX 后 OCR 结果不出现 / 耗时 39 秒」

> 用户反馈（2026-11-12 12:16 / 12:19）：
> 「截图很流畅 但是现在怎么不会出现ocr的结果了」
> 「我是用游戏内的截图试的 为什么耗时会这么久 昨天成功的那个版本基本上五六秒就行了
> 现在把截屏改成 sharex 反而不行了」

## 一、结论

**不是 ShareX 式选区导致的，也不是 OCR 变慢了。** 分段计时发现两个独立问题：

1. 价格历史装配把每个 `.gz` 快照按物品数重复解压，匹配数一多就爆炸（39 秒的真凶）；
2. 原生选区松手后**没有任何反馈**，用户等不及按热键，热键又把刚出现的浮窗关掉了
   ——所以「结果不出现」。

## 二、分段计时（不猜，逐段测）

| 环节 | 昨天尺寸 977×598 | 今天尺寸 1423×836 |
|---|---|---|
| `engine.recognize()` | 0.75s | 3.99s（>1200 触发分块） |
| `matcher.match_lines` | 0.10s | 0.24s |
| `snapshot_for` | 0.04s | 0.00s |
| **HTTP 墙钟** | **19.23s** | **23.89s** |
| BFF 回报 `tookMs` | 494ms | 3655ms |

`tookMs` 与墙钟差 15~20 秒，说明慢在 OCR **之后**的装配。继续拆：

```
price_history.series(days=3, 10 ids)  = 1.97s
price_history.series(days=30, 10 ids) = 1.98s
price_history.series(days=3, 60 ids)  = 10.00s
price_history.series(days=30, 60 ids) = 14.07s   → 合计 24s
```

根因在 `series()` 的 collector 分支：对每个 `(快照文件, 物品 id)` 调用一次
`_gz_rows()`，而 `_gz_rows` 每次都 `gzip.open(path).read()` 全文解压再 `find`。
本机 3 天窗口有 **142** 份 gz、30 天 **174** 份，60 个物品 → 约 **8500 次解压**。
缓存 key 里带了 `item_id`，完全挡不住。

所以昨天 21 件匹配 ≈ 5 秒，今天 81 件匹配 ≈ 39 秒 —— 成本随匹配数线性增长，
与 ShareX 改造无关，只是这次框选更大、匹配更多才暴露出来。

宿主日志也印证了「结果不出现」：

```
12:11:03 识别完成：81 件 / 39160 ms
12:11:03 透明浮窗已显示 81 件
12:11:03 选区窗已显示 8 ms      ← 同一秒用户又按了热键 → sess.close() 关掉浮窗
12:11:05 选择已取消
```

## 三、修复

### 1. 一份 gz 只解压一次（`tools/price_history.py`）

- 新增 `_gz_rows_batch(path, wanted)`：一次解压 → 批量 `find` 出所有目标行；
  按 `(path, mtime, size)` 缓存解压文本（上限 24 份，不再按 id 分裂缓存）。
- `series()` 的 collector 分支改调它；`clear_cache()` 同步清文本缓存。

实测 `series(60 ids, 30d)`：**24s → 0.41s**（二次调用 0.31s）。

### 2. 30 天 / 72h 合并成一次扫描（`tools/serve.py`）

原来 `days=3` 和 `days=30` 各调一次 `series`（所有 gz 解压两遍）。现在只调
`series(days=30)`，用返回 `points` 的时间戳本地切出最近 3 天求 `w72` 均值，
`w30d` 用全窗口；语义不变，解压次数再减半。

### 3. 识别反馈与防重入（`tools/scan.py · watch_native`）

- 松手立刻显示 **「识别中…  W × H」** 提示条（复用预热的 role 5 小窗，零成本）；
- 识别放**后台线程**，主消息循环继续响应；结果回主线程后才创建 `OverlaySession`；
- 识别中按热键不再重开选区、不再 `sess.close()` 误关浮窗（日志明确记「按键忽略」）；
- 识别失败也隐藏提示并写日志，不会静默卡住。

## 四、效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 1423×836 HTTP 端到端 | 23.89s（用户实测 39s） | **5.69s**（松手→结果实测 3.0s） |
| 977×598 | 19.23s | **3.23s** |
| `series(60 ids, 30d)` | 14.07s | **0.41s** |
| 松手后反馈 | 无 | 「识别中…」提示条，150ms 内可见 |
| 结果浮窗 | 会被下一次热键关掉 | 防重入保护 |

> 昨天体感 5~6 秒，现在同尺寸 3.2 秒、更大选区 5.7 秒，已恢复并略优。
> 剩余时间主要是 OCR 分块识别本身（`tookMs` 0.5~4s），与历史装配无关。

## 五、验收

- `tests/test_r248_batch_history.py` 4 条：批量接口存在、`series` 走批量、
  **monkeypatch 计数 `gzip.open` 证明 N 个物品只解压一次**、serve 只调一次 `series`、
  `watch_native` 有后台线程/提示/防重入；
- `tests/test_r238_scan.py` 的多窗口价格契约按新实现更新（一次 30 天 + 本地切 72h）；
- 端到端注入热键 + 拖拽：热键→选区 37ms、松手 150ms 内提示条可见、
  松手→结果 3.0s、日志 `识别完成 … / 2927 ms`；
- 单独用假 matches 验证 `OverlaySession.show()` 仍能正常渲染两行价格与控制条
  （`docs/r248/02-result-overlay.png`）。

## 六、说明

- 本轮测试时桌面显示的是中文应用界面，框选区域没有游戏物品名，故端到端样例为
  `0 件`；真实游戏截图经同一 BFF 接口验证过 10~20 件匹配，浮窗渲染另做独立验证。
- `MAX_ITEMS = 60` 仍限制单次历史查询的物品数（超出部分无 72h/30d 均值，显示 —），
  这是既有上限，不影响最新价/24h 均价。
- BFF 与扫描宿主均已重启生效。
