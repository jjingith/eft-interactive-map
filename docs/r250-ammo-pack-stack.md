# R250 · 弹药名按数量形态区分「弹药包」与「散装堆叠」

用户反馈（2026-11-12 13:50）：

> 现在这些子弹实际上游戏里是不能上架跳蚤的，能上架的是弹药包。
> 弹药包是有 25/25 30/30 120/120 这类显示弹药包子弹数的；不是弹药包而是散装的
> 弹药，下面只会显示不带 / 的堆叠数量。加一个判断：如果是识别到属于弹药类的
> 名字，再加个判断看下面有没有这种代表弹药包的 xx/xx —— 有就显示弹药包的价格，
> 没有就显示单发弹药的商人收购价格乘下面显示的弹药堆叠数量。

## 一、问题根因

短名索引（`data/ocr-item-names.json`）里，同一段游戏内文字同时指向多件物品：

| OCR 短名 | 散装子弹（`ts` 含 `ammo`） | 弹药包（`ts` 含 `ammoBox`） |
|---|---|---|
| `BS` | 5.45x39毫米 BS（`sl` 351 ₽） | 30/120 发装 BS 弹药包 |
| `BT` | 5.45x39毫米 BT（243 ₽） | 30/120 发装 BT 弹药包（跳蚤 87,777 ₽ 等） |
| `M856A1` | 5.56x45毫米 M856A1（191 ₽） | 50/100 发装 M856A1 弹药包（59,999 / 133,999 ₽） |

旧逻辑在同名候选里按「每格价最高」挑，于是**散装子弹被错配成弹药包的跳蚤价**
（80 发 BT 显示成 120 发装弹药包的 87,777 ₽）。散装子弹本身禁售跳蚤，
R249 的商人价兜底也因为选错了候选而给不出正确数量级。

## 二、判据与实测几何

用 `ui图标/ocr测试专用游戏内截图.png`（3840×2160）的仓库区实测：

- 物品名印在格子**右上角**，数量印在**同一格右下角**，两者**右沿对齐**；
- 4K 实测：名字 `y=42`、数量 `y=138`（dy≈96px ≈ 0.76 格），格宽 126px、
  OCR 行框高 22px；相邻行的数量在 `y=264 / 390 / 516`，间隔同样 126px；
- 弹药包数量带斜杠：`30/30`、`120/120`、`25/25`；散装堆叠是纯数字：`80`、`21`、`24`。

因此关联规则（`_ocr_ammo_count()`）：数量行必须满足
`1.5×行框高 ≤ dy ≤ 8×行框高`（分辨率无关）且
`|数量右沿 − 名字右沿| ≤ 3.2×行框高`（≈70px，小于 126px 格宽，自动排除邻格）。

## 三、实现（`tools/serve.py`）

- `_ocr_ammo_kind(rec)`：`ammoBox` → `"pack"`；仅 `ammo` → `"loose"`。
  少数弹药包 `ts` 同时含两者，必须**先判 ammoBox**。
- `_ocr_count_lines(lines)`：从 OCR 原始行挑数量行。带斜杠 `^(\d{1,4})/(\d{1,4})$`
  = 弹药包；纯数字 = 散装堆叠。只做保守字形归一（`O→0`、`l→1` …），
  且要求原文含数字或斜杠，避免把 `BS` / `33.2/58`（护甲耐久）/ `子弹/弹匣/狗牌/钱`
  （栏位标题）/ `1,000`（价格标签）当数量。整张图只扫一次。
- `_ocr_ammo_decision()` → `(kind, qty, narrowed_ids, count_found)`：
  - 候选里没有弹药类 → 完全不干预；
  - 找到 `xx/xx` → `"pack"`，并用 `_ocr_prefer_pack()` 按 `30/30 → 30发装`、
    `120/120 → 120发装` 缩小到对应规格；显示该弹药包价（跳蚤价优先，
    禁售跳蚤则按 R249 显示商人收购价）；
  - 找到纯数字 N → `"loose"`，`qty=N`，整体价 = 单发商人收购价 × N；
  - 只有 `xx/xx` 却没弹药包候选，或反过来 → 退回原逻辑，不臆造；
  - 数量行没识别到 → 仍判散装，但按 1 发保守计价并标 `qtyFound=false`。
- `_ocr_prefer_loose()`：`BP` 同时有 5.45x39 / 7.62x39 / 9x39 三个散装候选，
  OCR 只读到 `BP` 无法分辨口径；按同短名弹药包的口径分布投票（BP 以 5.45x39 为主）
  做确定性推断，比「挑单价最高的」贴近实际。
- `_ocr_apply_ammo_stack()`：把 `priceSource=trader`、`trader=单价×数量`、
  `unitPrice`、`qty`、`qtyFound`、`ammoStack=true` 写回 price，并清空 `w72/w30d`
  （商人一口价，没有历史窗口）。浮窗因此照常显示红色购物车小图标。
- `POST /api/ocr/overlay/state` 白名单加 `ammoKind` / `qty`；`js/market.js` /
  `market.css` 结果表加「散弹×80」「弹药包 30发」标记与计算说明 tooltip。

`tools/scan.py` **无需改动**：`price_views()` 走 `priceSource=trader` 分支读
`price.trader`，四种口径都显示整堆商人价。

## 四、验收

真实 4K 截图裁 `840×650`（4 行完整仓库，含各自数量行），临时 8799 端口端到端：

| OCR | 数量 | 结果 |
|---|---|---|
| BS | 80 | 351 × 80 = **28,080 ₽** |
| BS | 21 | 351 × 21 = **7,371 ₽** |
| BT | 15 | 243 × 15 = **3,645 ₽** |
| BP | 19 | 283 × 19 = **5,377 ₽**（口径推断到 5.45x39） |
| M856A1 | 80 | 191 × 80 = **15,280 ₽** |
| M995 | 56 | 553 × 56 = **30,968 ₽** |

31 件匹配里 30 件判为散装，24 件成功读到数量行（其余 6 件位于裁图最下沿，
其数量行在图外，按 1 发保守计价并标 `qtyFound=false`；完整选区不会有此问题）。

**弹药包分支**：把某个 BS 格子的 `80` 改成 `30/30` 合成一张验收图
（`build/_r250_pack_synth.png`）跑同一接口 → 该格判 `ammoKind=pack / qty=30`，
选中「5.45x39mm BS弹药包（30发装）」并显示 450 ₽；同排另一格 `21` 仍是
散装 7,371 ₽。两种形态在同一张图里互不干扰。叠加验收图
`build/_r250_overlay_preview.png`。

**回归**：新增 `tests/test_r250_ammo_pack_stack.py` 13 条（形态分类 / 数量行噪声
过滤 / 同格几何关联 / 散装与包两种决策 / 按包规格与口径缩小候选 / 单价×数量 /
四口径一致 / 白名单与前端契约）；`test_r249_overlay_xp_trader.py` 的白名单断言
随新字段迁移。全量 `build/_pytest_r250.xml`。

## 五、边界

- 同一短名对应多个口径的散装弹（BP / BT 等）无法从文字判定，按弹药包口径分布
  推断；`price.name` 会写明最终选中的具体物品，便于核对。
- 数量行没识别到时按 1 发计价（`price.qtyFound=false`），市场页 tooltip 会说明；
  界面上不会假装读到了数量。
- `xx/xx` 也会出现在弹匣/护甲耐久等处（实测 `60/60`、`335/340`），但它们不与
  弹药名的右沿/行距同时匹配，且非弹药名根本不进入本判断。
- 本轮只改价格装配，未改浮窗排版、未改契约 JSON、未 commit/push/打包。
