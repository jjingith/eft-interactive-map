行内信息（实测截图 01/02/06/09）：

- 名称左侧显示物品图标；名称下方两行小字：`Updated N mins/hours/days ago` + **逐物品来源** `tarkov-market` 或 `tarkov.dev`。
- 来源是**逐物品选择**的：有 tarkov-market 数据就显示 tarkov-market，否则回落 tarkov.dev（L15170–15183、L163105 附近）。同一页里两种来源会混排。
- `manualPrice` 列出现 `S` / `P` 两个小按钮（行内编辑卖价/买价），仅部分行显示。
- `Related / Copy / Stock / Fav` 为图标按钮；`Stock` 显示"标记缺货"，补货后自动复位（L163882 文案）。
- 空搜索/无匹配：**只有表头，表体全黑，没有任何提示文案**（实测截图 09）——这是可改进点。
- 加载态：居中转圈 + `Checking` + `Season Flea Market`（实测首屏；截图交互窗口内已缓存，未再复现）。
- 429：历史价格请求限流时显示 `Too many requests. Try again in 1 minute.`（L101340 附近）。
- `noFlea` 物品：显示 `Banned` 徽标，不显示价格与曲线（L15133 等）。

### 1.3 "Lv" 字段来源（实测确认）

不是交易员忠诚等级，而是 **`minLevelForFlea`（跳蚤市场最低玩家等级）**：

- db4 自家 `json/core/items.json` 单条样本（实测拉取一次，6.9 MB）：
  ```json
  {"id":"69bb3f7df94327bc0f0230c9","name":"Compartment C-3 keycard",
   "types":["keys"],"minLevelForFlea":30,
   "sellFor":[{"vendor":{"name":"Therapist"},"priceRUB":336600}],"weight":0.01}
  ```
- UI 该行 `Lv=30`，与 `minLevelForFlea` 完全一致（截图 09 第 1 行）。
- 过滤器 `a.ax <= 玩家等级`，`ax` 即该字段（L163769）。

`Buy From` / `Sell For` 的具体取数（trader `buyFor`、`sellFor`、还是跳蚤最低价）在截图与静态代码里存在交叉歧义，**本步标为待核对**，实现该列前用一条真实物品逐格比对，不做猜测。

priceSetting=0, market_isGridView(未设), market_autoRefresh(未设=关)

## 4. 与本项目的对照（决定复刻边界）

### 4.1 现有可复用资产

| 层 | 现有实现 | 复用方式 |
|---|---|---|
| 物品元数据 | `data/items.json`（5480 件，紧凑键 `n/sn/ic/gw/gh/w/p/ts/src/trade/dur/cats/...`） | **直接复用** |
| 价格快照 | `data/flea-prices.json`（5124 条，`lastLowPrice/avg24hPrice/low24hPrice/high24hPrice/basePrice`） | **扩展后复用**，不新建数据层 |
| 价格读取 | `app.js` 内 `fleaQuoteOf(id)` / `fleaLevelOf(id)` / `overlayQuoteFields` | **扩展后复用** |
| 在线行情（可选） | `tools/live_prices.py` + `/api/live-prices`（服务端开关） | 市场模块沿用同一开关与覆盖逻辑 |
| 构建抓取 | `tools/r20_fetch_prices.py`（`json.tarkov.dev/regular/items`） | **扩展字段**，不新增抓取器 |

### 4.2 字段缺口

| 页面需要 | 现有数据 | 处置 |
|---|---|---|
| Last Price / Avg 24h | 有 | 直接映射 |
| Avg 7d | **无** | 构建期扩展抓取 `avg7daysPrice` |
| 逐物品 `updated` | **无**（只有整体 `lastSuccessAt`） | 构建期补 `updated`，并写 `meta.sourceUpdatedMax` |
| `minLevelForFlea` | **无**（现有 `trade.l` 是忠诚等级 1–4） | 构建期从上游 items 补该字段 |
| 72h 曲线 | **无** | 运行期禁止联网 → 用**自建快照历史**（构建/本地定时追加），首版显示"数据积累中" |
| Buy From / Sell For | 部分（`trade` 买卖/以物易物） | 用现有 `trade` 合成；语义逐格核对后再定 |
| Stock / Restock | **无** | 首版不做，列留空或隐藏（不伪造） |
| 图片/CDN 资源 | 本地图标 sprite（`ic`） | 用本地图标，不引用 db4/tarkov.dev 图片 |
| 逐物品来源切换 | 只有 tarkov.dev | 不做双源；统一标 `tarkov.dev 快照` |

### 4.3 必做差异化（本任务要求）

- `flea-prices.json` 顶层新增：
  ```json
  "meta": {
    "generatedAt": "2026-11-08T06:00:00Z",
    "sourceUpdatedMax": "2026-11-08T04:48:00Z",
    "source": "json.tarkov.dev/regular/items"
  }
  ```
- 市场页固定显示「**数据截止 04:48（3 小时前）**」，悬停显示生成时间与来源。
- 空态明确文案（db4 此处是纯黑，我们补「没有匹配的物品 · 清空搜索」）。
- 数据过期超过阈值（建议 6 小时）用琥珀色提示，不假装实时。

### 4.4 不学的三件事

1. 381 KB × 4 变体重复文件 → 我们单表 + 模式字段过滤；
2. 前端逐物品直连上游取历史 → 我们只读本地；
3. 伪实时（15 分钟客户端刷新掩盖 40–70 分钟服务端快照）→ 我们显式标注数据截止。

### 8.4 本轮对比暴露并已修的三个问题

1. **服务端 view 白名单未同步**（见 8.3 第 1 行）——前端与 `tools/config.py` 两处 `VIEWS` 必须一起改。
2. **短名直接用了 `rec.sn`** → 显示成 `5a16… ShortName`；改为与 `app.js` 同一套 `shortNameOf` 推导。
3. **价格单元格被 `cell()` 覆盖 className** → 丢右对齐/列宽规则；改为保留 `mk-col-price`。

另：**Lv 默认由 20 改为 40**。证据是 db4 截图中滑杆手柄停在最右刻度、且 Lv 25/30 的行照常显示；默认 20 会把 Lv 25+ 整段藏掉（连 `ledx` 都搜不到）。

### 8.5 首版明确差异（不是缺陷）

## 9. avg7d 与历史归档决策

不额外抓上游 72h 做首版填充，理由：

1. 上游 `items` 只有当前快照，**没有 `avg7daysPrice`，也没有 72h 历史字段**；db4 的曲线另用第三方（tarkov-market）来源，本任务不复用其接口；
2. 对 3540+ 件逐物品再拉一次历史，必然触发 429 且把构建时间拉长到不可控；
3. 混用外部历史会破坏「自有快照」口径。

因此每次构建期抓取顺手落一份带本地时间戳的归档（`data/flea-price-history/2026-11-08T144256.json`），保留 90 天；满 7 个快照日后按快照日 `lastLowPrice` 求均值，**缺日不计算、不插值、不估算**。日内多份快照也为后续 72h 曲线保留了真实样本。

## 10. 经验教训

1. **这类 Flutter / Canvas 页面的逆向入口是读 `main.dart.js` 的静态字符串表**：列名、价格口径枚举、Lv 过滤方向（`minLevelForFlea` 与玩家等级比较）都来自那里；DOM 解析与截图只用于验证视觉，不要在 DOM 上反复尝试。
2. 视图是**两处硬编码**：`app.js` 的 `VIEWS` 与 `tools/config.py` 的 `VIEWS`；漏一处会出现「点了没反应/被回填重置」，必须同步并加测试。
3. 截图脚本要等共享配置回填稳定后再点击视图，否则会把「被重置」误判成「按钮没绑定」。
4. **JS 里不能出现 `http://` / `https://` 字面量**（离线契约测试会直接失败）。需要展示来源 URL 时从 `flea-prices.json` 的 `meta.source` 动态取，或在注释里避开协议前缀。

## 13. R223：删除「Collected 计数（仅本机，不跨设备）」

### 13.1 为什么删

这块是 R97 对齐参考站时**按结构照搬**的（参考站详情面板左列有 `Collected: FIR [− 0 +] non-FIR [− 0 +]`）。我们没有游戏内存/存档的读取通道，所以它只能做成手点计数器，写 `localStorage['eftmap.market.collected.v1']`；R19.47 拍板「保留但标注范围」，于是加了标题限定、`未记录` 徽标与免责说明。

标注是诚实的，但**功能是空的**。删除前用真实浏览器探针实测（7/7 通过）：

| 实测项 | 结果 |

| 初始状态 | `0 / 未记录`、`0 / 未记录` |

| 落盘 | `{"<itemId>":{"f":2,"n":0}}` |

| 页面其它地方是否消费 | **没有**：行内无徽标、工具栏无「只看已收集」筛选、无导出 |

结论：它是**只写不读**的计数器——除了让数字变一下，对「查行情」这件事没有任何帮助；而 3540 个物品每个打开都显示 `0 / 未记录`，反而像在陈述「你一件都没有」。

## 14. R224：时间轴按区间铺满 + 断档不连线 + 页脚去歧义

### 14.1 症状

用户反馈：**24 小时 / 7 天 / 30 天 三条曲线长得一模一样**；并且要求「如果是因为没有数据，那也要完整显示时间轴，没数据的部分就不显示线」。

### 14.2 根因

`drawHistoryChart()` 把**数据首尾**当成了时间轴两端：

```js
var t0 = parseTime(rows[0].t).getTime();
var t1 = parseTime(rows[rows.length - 1].t).getTime();
```

接口本身是对的（`days=1` → 47 点、`days=7` → 86 点、`days=30` → 86 点），但本地只有约 2 天数据，**7 天与 30 天返回的是同一批 86 个点**，被分别拉伸到整条画布 → 渲染结果像素级雷同；24h 同样是拉满，只是点多一点，看起来也「差不多」。

### 14.3 改法

| 改动 | 说明 |
|---|---|
| `histWindow(windowStart, days, points)` | 有区间就返回 `[windowStart, windowStart + N 天]`；`days=0`（全部）才退回数据首尾；`windowStart` 缺失时按最后一点回推，仍不拉满数据 |
| `X(t)` | 用窗口换算坐标；窗口外的点贴边裁掉，异常时间戳不会把轴撑大 |
| 横轴刻度 | 起点 / 中点 / 终点三个，全部来自窗口（`mk-hist-axis-x`） |
| `histGapMs()` / `histSegments()` | 以采样间隔**偏低中位数**为基准，阈值 `max(45 分钟, 2.5 × 基准)`；超过就切段 |
| 绘制 | 每段单独 `M…L…` 与独立面积；**孤立采样画一个 r=2 的点**；段与段之间不连线、不补点 |
| 页脚 | 去掉「覆盖 N 天」，改成「区间 A → B（24h）· 样本 N 个 · 有数据 23 小时 30 分（占 98%）」；占比 < 60% 时补一句「只有 X 有采集，其余 Y 没有样本」 |
| 口径说明 | 合并为一句：「线 = 最近低价，悬浮看 24h 均价；采样点之间是直线，不是逐笔成交；没有样本的时间段不画线，数据来自本机采集、非实时」 |

### 14.4 那行旧页脚到底在说什么（用户提问）

旧文案：`样本：46 个快照（采集器 46 份） · 窗口 24h · 覆盖 2 天 · 11-09 15:31 → 11-10 15:01`

- **样本 46 个**：窗口内参与画线的快照数；
- **窗口 24h**：所选区间；
- **覆盖 2 天**：`coverageDays` 是「覆盖到的**自然日**个数」（11-09、11-10 各算一天），**不是时长**——所以和「24h」并列时读起来像自相矛盾；
- **11-09 15:31 → 11-10 15:01**：**数据**的首末时间，不是窗口的首末（窗口其实是 11-09 15:10 → 11-10 15:10），和「窗口 24h」也对不上。

四段口径混在一行里，每一段都真，合起来却像在打架。现在改成只用一种口径：窗口首末 + 有数据时长 + 占比。

### 15.3 单点情况的一处连带修正
